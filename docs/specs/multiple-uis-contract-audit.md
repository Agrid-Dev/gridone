# Audit des contrats consommés par les interfaces Gridone

Annexe de la [proposition AGR-1597](multiple-uis-research.md), au 8 octobre 2026. Les constats portent sur Gridone `51546eeec497efcf6da64955adf0b013435a1f6c`, le tag `v0.246.0` (`f46254f4e003a479d57f66c103c503857d5c2a67`) et `gridone-charles` `33145c048f1e322254c8161e5076a9f5c8f6f484`.

**Méthode :** lecture du code et des workflows, comparaison Git des routes, modèles et types OpenAPI TypeScript versionnés, examen des tests et notes historiques. Les documents du dépôt sont des sources à confronter au code ; leurs prompts et listes de tâches ne sont pas des instructions exécutées. Aucun test applicatif, appel aux box ou essai de commande n’a été effectué.

## Contrat consommé par l’UI hôtelière

Les chemins suivants sont ceux de l’API ; le navigateur leur ajoute `/api`. Le proxy CloudFront/nginx hôtellerie conserve ce préfixe vers la box, puis le nginx Gridone le retire avant FastAPI. Les méthodes SDK sont résolues à partir de leurs implémentations, pas seulement de leurs noms.

### Authentification et autorisations

Les deux UI ont un `CookieTokenStorage` qui conserve les JWT dans `gridone_access_token` et `gridone_refresh_token`, accessibles au JavaScript. Ces cookies sont distincts des cookies `access_token` et `refresh_token` HttpOnly émis par l’API. Le SDK utilise le bearer et le refresh ; le WebSocket reçoit le JWT par sous-protocole, sans fallback aux cookies HttpOnly. Le proxy permet les appels de même origine sans exiger d’élargir le CORS à tous les sites. [Stockage hôtellerie][h-tokens], [stockage généraliste][g-tokens], [auth API][g-auth].

L’UI généraliste vérifie les permissions de `/auth/me`. L’UI hôtelière applique `accessOf` : `viewer` en lecture, `receptionist` limité aux usages de confort, tout autre rôle avec accès UI complet. Le backend courant possède des rôles personnalisés, des scopes de lecture et une permission de commande distincte. L’`operator` intégré ne possède pas `automations:write` ; être opérateur suffit à certaines commandes, pas à la création d’automatisations. Les choix affichés doivent donc dépendre des permissions effectives. [Auth généraliste][g-auth-ui], [accès hôtellerie][h-access], [rôles serveur][g-roles].

Un 401 avec challenge bearer déclenche le renouvellement ; un 403 peut être un refus d’autorisation ; un 404 peut correspondre à une ressource masquée par le scope ; un 422 peut être une erreur de forme ou un refus métier. Les erreurs HTTP et les commandes retournées avec `status: error` sont deux voies différentes. Les diagnostics structurés `reasons` ajoutés au SDK courant ne sont pas exploités automatiquement par l’archive ancienne. [HTTP][g-http], [erreurs SDK][g-errors], [envoi hôtellerie][h-send].

### WebSocket et conventions métier

L’UI hôtelière traite `device_update` (valeur/timestamps), `device_full_update`, `device_list_update` et `device_write_state` (révision, états, résolutions). Les types inconnus sont ignorés. Les messages `device_write_state` plus anciens que la révision détenue ne sont pas appliqués. Après une coupure, les requêtes appareils et historiques sont invalidées ; avant reconnexion, `/auth/me` permet le refresh. Le contrat du flux est recopié dans les UI et n’est pas couvert intégralement par les types HTTP OpenAPI. Le serveur courant projette les messages selon le rôle de la connexion. [Consommateur][h-socket], [connexion][h-device-context], [schémas serveur][g-ws], [projection][g-ws-manager].

Les profils de compatibilité doivent aussi couvrir les attributs métier : consigne, marche/arrêt, modes, bornes et pas ; tags de zones ; conventions de points eau chaude/PAC/ventilo-convecteurs. Le menu avancé dépend d’une structure précise du driver, contrôlée par `menuSupported` ; ce résultat est mis en cache avec `staleTime: Infinity`. Une mise à jour de driver peut donc exiger une invalidation même si Gridone n’a pas changé de version. Ne pas inscrire des noms de fabricant dans un registre de capacités backend. [Détection du menu][h-menu-support], [cache du driver][h-menu-hook].

## Évolution depuis v0.246.0

La comparaison des chemins des types OpenAPI versionnés ne montre aucun chemin retiré ; elle montre néanmoins des ruptures de forme et de comportement. La stabilité des URL ne constitue donc pas une garantie suffisante. Les types générés ont été confrontés aux modèles Python et aux consommateurs concernés.

| Changement établi dans Git                                                                                                             | Classification                                                      | Effet sur les consommateurs                                                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AutomationCreate.action` remplacé par `branches` obligatoire ; `AutomationUpdate.action/enabled` retirés                              | **Incompatible pour les anciens payloads**                          | Ancienne création sans `branches` non conforme au modèle courant ; inversement, le frontend hôtellerie courant envoie `branches` sans l’`action` exigée par `v0.246.0`. Un ancien patch portant seulement `action`/`enabled` n’exprime plus la même mutation. |
| `automationBody()` hôtellerie émet `branches` puis caste en `AutomationCreate` ancien ; `actionOf()` sait lire les deux formes simples | **Adaptation existante, garantie partielle**                        | Le correctif de lecture ne signifie pas que l’écriture fonctionne sur les deux contrats. `pushRemote` supprime les anciens objets avant de recréer : établir la compatibilité avant cette opération.                                                          |
| `ExecutionStatus` gagne `no_match`, `initialized`, `tripped`, `skipped`                                                                | **Potentiellement incompatible sémantiquement**                     | Le composant `Where` hôtellerie traduit tout statut autre que `failed` par `lastDone`, ce qui ne distingue pas une exécution ignorée ou un garde déclenché.                                                                                                   |
| `DeviceWritePreview.reason` remplacé par `reasons[]`, contraintes résolues et `write_state`                                            | **Incompatible pour le diagnostic du repli preview**                | `useModeAvailability` lit encore `member.reason`; les refus deviennent non qualifiés. Le chemin `write_state` utilisé en priorité réduit la portée, sans corriger ce repli.                                                                                   |
| Règles d’écriture déclaratives, observation/dépendances, operating rules                                                               | **Changement de comportement à qualifier**                          | Une écriture autrefois acceptée peut être refusée ou demander une décision sur un état inconnu. Ce peut être une règle métier légitime, pas un défaut de transport.                                                                                           |
| Preview unitaire, `ui_confirmation_token`, langue et avertissement déclaratif                                                          | **Additif au protocole, écart fonctionnel entre UI**                | L’UI généraliste montre le consentement prévu ; le dispatch direct hôtellerie ne reproduit pas ce parcours. L’absence de preuve de confirmation UI n’entraîne pas à elle seule un rejet serveur.                                                              |
| Consentement aux operating rules inconnues, lié à un preview                                                                           | **À qualifier par parcours**                                        | Ce consentement métier est distinct de l’avertissement UI et du booléen `confirm` de relecture matérielle. Ne pas les fusionner.                                                                                                                              |
| `MeResponse.role` devient une chaîne libre ; permissions de commande séparées ; scopes sur lectures HTTP/WS                            | **Potentiellement incompatible pour une UI fondée sur trois rôles** | Commandes visibles à tort, attributs absents, historique partiel et 404 attendus pour un compte restreint. L’API demeure l’autorité.                                                                                                                          |
| `BuildingProfileRead.timezone`                                                                                                         | **Ajout toléré, fallback à qualifier**                              | Hôtellerie le lit hors ancien type et conserve la valeur localement. En son absence, timezone navigateur ; vérifier les horaires si les deux diffèrent.                                                                                                       |
| Transport auth, chemins token/me, sous-protocole bearer ; enveloppes de base du flux conservés                                         | **Continuité observée par lecture**                                 | Le contrat de base subsiste, mais les permissions et la projection évoluent. Cela ne certifie pas une combinaison navigateur/proxy/release.                                                                                                                   |
| Nouveaux endpoints de rôles, operating rules, diagnostics, structure dashboards                                                        | **Ajouts pour les clients existants**                               | Une nouvelle UI les consommant ne peut pas en déduire leur présence sur un backend ancien.                                                                                                                                                                    |

## Distribution et tests existants

La publication hôtellerie archive sous `releases/<sha>/`, puis copie assets, fichiers publics, HTML et enfin `sw.js` vers `live/`. Les hashes sont contrôlés, les publications sont sérialisées, les assets historiques ne sont pas supprimés. La copie multi-fichiers n’est pas atomique. L’origine API est sélectionnée par hostname et les réponses API ne sont pas mises en cache par le CDN. La correction `Secure` des cookies de l’API au niveau edge est une adaptation d’infrastructure documentée, pas une garantie de toutes les versions backend. [Publisher][h-publish], [routage][h-route], [déploiement][h-deploy].

La PWA garde le shell, exclut `/api` du fallback et propose l’update à l’utilisateur, avec vérification au démarrage, retour à l’app et périodiquement. Le cache React Query en mémoire peut cependant conserver des mesures précédentes. Le moteur `localStorage` documente la préservation des formes existantes et ne s’abonne pas aux changements d’autres onglets. Des automatisations simples sont désormais publiées sur le serveur ; le README affirmant que toutes restent locales est donc incomplet pour le checkout inspecté. D’autres configurations/brouillons/préférences restent locaux. [PWA][h-vite], [update][h-update], [stockage][h-store], [synchronisation][h-automation].

## Inventaire complémentaire de l’UI généraliste

L’UI généraliste consomme le SDK local du même arbre. Outre auth, health et WebSocket, les domaines ci-dessous sont présents dans ses appels. Les chemins sont des familles ; le fichier SDK lié définit chaque méthode et sa forme HTTP. Les identifiants entre accolades sont des paramètres, pas des routes supplémentaires.

| Domaine         | Appels observés et familles d’endpoints                                                                                                                                                                            |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Appareils       | CRUD `/devices/` et `/{id}` ; tags, groupes de tags, affectation aux assets ; types standard ; faults ; attributs/refresh ; présentations et leurs ressources ; `/devices/commands`, preview/confirm et templates. |
| Assets          | CRUD `/assets/`, arbre avec appareils, ordre des enfants, usages, profil et schéma ; modèles bâtiment, scène, import, régénération, upload et suppression.                                                         |
| Automatisations | CRUD, activation/désactivation, `/schema`, `/triggers`, historique `/executions` et `/diagnostics`.                                                                                                                |
| Device views    | CRUD `/device-views/` pour les vues/groupes de devices.                                                                                                                                                            |
| Drivers         | Lecture/liste/suppression `/drivers/`, installation/export des paquets, présentations et assets de présentation.                                                                                                   |
| Transports      | CRUD `/transports/`, schémas, reconnexion, création/liste/suppression des discovery handlers.                                                                                                                      |
| Timeseries      | Séries et points sous `/devices/`, agrégations temporelles/spatiales/live, options et export CSV/PNG.                                                                                                              |
| Dashboards      | CRUD `/dashboards/`, structure, schémas de widgets, ajout/édition/suppression de widget et layout.                                                                                                                 |
| Synoptiques     | Liste, lecture, création et remplacement `/synoptics/`.                                                                                                                                                            |
| Operating rules | CRUD, schémas, activation et historique `/operating-rules/`.                                                                                                                                                       |
| Utilisateurs    | CRUD `/users/`, liste des rôles, block/unblock, changement du mot de passe `/auth/password`.                                                                                                                       |
| Notifications   | Liste et dismiss `/notifications/`.                                                                                                                                                                                |
| Apps            | Liste/lecture/activation/configuration `/apps/`, schémas, demandes d’enregistrement acceptées/rejetées.                                                                                                            |
